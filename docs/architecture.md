# 程序架构

Cataland 的一间房间由一台玩家电脑主持。Rust 保存并计算对局，React 展示每名玩家能够看到的信息，PixiJS 绘制棋盘。房主与客机使用同一套动作和状态类型，区别在于本机后端如何到达房间。

玩法见[游戏规则](rules.md)，环境准备和修改流程见[开发指南](development.md)。

## 运行结构

```text
房主电脑
React 界面 → Tauri 命令 → 本机 Host → Room → Game
                 ↑         │
                 └── 面向房主的状态与事件
                           │
                     WebSocket 房间服务
                           │
客机电脑                   │
React 界面 → Tauri 命令 → Rust WebSocket 客户端
                 ↑
                 └── 面向该席位的状态、事件与聊天
```

房主的界面直接通过本机后端访问 Host，客机通过本机 Rust 网络客户端访问房主。两条路径都接收 `Response`，并采用同一个合并过程形成客户端状态。

程序按三个目录组织。

| 目录 | 职责 |
| --- | --- |
| `crates/core` | 棋盘、玩法、房间成员、动作、事件、玩家视图、共享类型 |
| `src-tauri` | 桌面启动、窗口、本机身份、存档、局域网发现、房主与客机通信 |
| `src` | React 页面、棋盘渲染、选择面板、动画、声音和本地化 |

规则核心依赖序列化、随机数和类型导出工具。文件访问、网络与窗口交给桌面层，因此完整规则对局可以独立于窗口运行。

## 核心数据

### 房间、席位与对局

`Room` 保存房间标识、设置、成员、聊天和可选的 `Game`。尚未开局时 `game` 为空。成员记录身份、玩家席位、连接情况和准备状态，首位成员是房主。

`Identity` 包含 `token`、名称和颜色。名称可以修改，席位关联依赖 token。同一 token 再次加入时连接到原成员。新成员在开局前且仍有容量时取得玩家席位，其他情况成为观战者。

`Game` 包含以下几组数据。

| 数据 | 含义 |
| --- | --- |
| `mode`、`humans` | 玩法与真实玩家数量；模式值为 `base` 或 `cities` |
| `board`、`buildings`、`roads`、`robber` | 地图拓扑与棋盘上的占用 |
| `players`、`bank`、`dev_deck` | 玩家财产、供应和基础牌堆 |
| `cities` | 城市与骑士状态，基础模式为空 |
| `stage`、`turn`、`pending` | 当前回合和等待选择的效果 |
| `trade`、`awards`、`winner` | 报价、分数奖励与结果 |
| `events` | 含公开和私有可见对象的完整事件历史 |

双人时，`players` 在两名真实玩家之后附加两名中立势力，`humans` 仍为 2。需要交互、计分获胜或发手牌的逻辑使用真实玩家数量；棋盘占用和道路竞争则可能涉及全部势力。

### 固定顺序与位置标识

`Cards` 是八个整数的数组，依次对应木材、砖块、羊毛、小麦、矿石、布匹、铸币、纸张。手牌、费用、银行与卡牌选择都使用这套顺序。基础模式的后三项为零。

地图由地块、顶点、边和港口组成。建筑与骑士以顶点索引定位，道路以边索引定位，强盗和商人以地块索引定位。`Target` 在这三种目标之间选择，因此渲染与动作都能直接使用相同的索引。

地图生成时先建立共用顶点和边，再填写相邻关系。绘图坐标附着在这份拓扑上；道路是否相连、建筑距离和骑士路径都根据拓扑计算。

## 回合与效果队列

`Stage` 有四种状态：`Setup`、`Production`、`Action`、`Ended`。初始放置额外记录轮次和正在连接的建筑，其他需要玩家选择的过程由 `pending` 中的 `Effect` 表达。

```text
Setup → Production → Action → 下一名行动者
             │           │
             └→ Effect 队列 ←┘
                    │
                指定玩家选择
                    │
             继续原来的回合流程
```

`Turn.player` 是当前行动玩家，`Turn.primary` 是本组回合的生产玩家。普通对局二者相同，五至六人的配对行动中二者不同。`Turn.number` 在每段玩家行动之间递增，发展卡购买时机、骑士本回合激活与晋升也用它判断。

`Turn.dice` 保存本回合已产生的生产骰。双人第一次生产结算完后仍进入 `Production`，第二次之后进入 `Action`。五至六人的配对行动沿用主回合骰子记录，新的主回合才清空它。

### 动作如何执行

页面发出 `RoomAction::Game`，其中携带 `Action`。`Room` 从连接身份找到玩家席位，再调用 `Game::apply`。

普通动作检查当前玩家、阶段、资源和位置。有待处理效果时，动作交给该效果解析。选择通过 `Pick`、`SelectCards` 或允许提前结束时的 `Skip` 提交。

`advance` 处理能够自动完成的效果，并在确实需要输入时停下。单一可选位置、空牌堆或已经没有合法目标的分支由规则模块处理。效果完成后重新计算奖项和胜利条件。

由此，移动强盗、选取偷牌对象、取得进步卡、归还超额卡、野蛮人城市损失和双人中立建设可以串接成同一条结算流程。队列本身可以序列化，存档能够停在这些选择中间。

### 多人响应

多人弃牌在队列前方形成连续的一组 `Discard`。参与者可以在同一组中按任意顺序提交，完成的条目把数量置为零，继续保留参与信息。

`Prompt.responses` 从这组条目生成玩家与完成情况。所有人完成后，这组效果才退出队列。由此，游戏规则和页面中的响应进度使用同一份数据。

### 一次对局修改的生效位置

`Game::apply` 负责规则运算，房间动作的提交过程位于 `Host::apply`。

```text
取得房间锁
  → 复制当前 Room
  → 在副本上执行 RoomAction
  → 将结果写入存档
  → 用结果替换房间状态
  → 通知本机与网络连接
```

规则返回错误或保存失败时，该次副本不成为房间状态。正常执行的状态与事件一起保存、一起发布。直接调用核心库的代码需要理解这个调用关系：房间提交由 Host 负责，核心动作本身提供规则操作与结果。

## 玩家视图

`RoomView` 包含房间设置、玩家席位、在线观战者、自己的席位编号、房主标记、聊天与可选的 `GameView`。其中没有成员的完整身份 token。

`GameView` 的公共部分包含棋盘、建筑、道路、银行、分数、手牌数量、回合和模式状态。`private` 提供自己的具体手牌、总分、卡牌、兑换汇率和城市发展选项。

`actions` 是该玩家可执行的普通动作，每项带标签、费用和可选地图目标。`prompt` 描述正在等待的选择。需要响应的玩家取得具体选项，其他玩家取得执行者与步骤说明。

观战视图的 `private` 为空，普通动作列表为空，仍能阅读公共局面。已结束对局的本地浏览也由公共视图产生，另外清除交互提示和未完成报价。

## 网络消息与增量历史

### 传输内容

网络传输使用 JSON WebSocket。连接建立后先发送 `Join`，其中包含身份及可选的历史游标，之后发送 `Action`。

```json
{
  "type": "join",
  "identity": { "token": "player-token", "name": "旅人", "color": 0 },
  "cursor": null
}
```

```json
{
  "type": "action",
  "action": { "type": "game", "action": { "type": "roll" } }
}
```

返回消息分为三类。

| 类型 | 内容 |
| --- | --- |
| `state` | 最新 `RoomView`，其中游戏事件只携带此次需要追加的部分，聊天另行发送 |
| `chat` | 房间标识、聊天起始位置 `offset`、新增 `messages` |
| `error` | 可翻译的 `Text` 错误 |

状态主体是完整的当前视图。增量处理适用于事件历史与聊天，因此持续对局的历史长度不会使每次动作都重复传输全部记录。

### 游标与消息合并

`Cursor` 记录房间标识、事件序号和聊天位置。事件序号是房间游戏中的全局递增序号；聊天位置是已经接收的消息条数。

游戏事件保存公开或指定玩家的可见范围。给某个席位生成历史时，先按序号取出后面的事件，再按可见范围筛选。因此一个玩家看到的事件序号可以有间隔。

服务端为每条连接保存游标和最近的房间修订计数。普通状态发生变化时发送当前视图与新的可见事件；只有聊天变化时发送聊天消息。`watch` 通知可以合并连续变化，而历史尾部仍由游标确定。

共享的 `Response::apply` 合并消息。同一房间、同一席位的新状态接在原有事件后面，并使用原有聊天历史；聊天消息从指定位置追加。切换房间或席位则使用对应的新视图。

同一客户端进程中的重连携带已接收游标。客户端重新启动后，历史从服务器重新取得，身份则从本机文件读取。

### 本机与网络的一致路径

房主连接通过 `Host::updates` 取得消息，客机连接从 WebSocket 读取消息。二者进入相同的桌面接收逻辑。

桌面层向 React 发出 `session`、`chat` 和 `notice` 三种事件。`session` 提供客户端状态，`chat` 只改变聊天数组，`notice` 显示动作错误。React 更新聊天时沿用原来的游戏对象，棋盘和棋局动效因此可以继续使用原状态。

相关实现见 [sync.rs](../crates/core/src/sync.rs)、[network.rs](../src-tauri/src/network.rs) 和 [session.ts](../src/session.ts)。

## 房间发现与连接生命周期

房主在系统分配的 TCP 端口监听，监听器使用双栈地址服务 IPv4 与 IPv6。局域网通过 `_cataland._tcp.local.` 发布和发现房间。

服务实例以房间 UUID 标识，主机名为 `cataland-<房间标识>.local.`。发现信息包含房间名、玩法、已占席位数、容量、是否开局以及可连接地址。IPv6 地址保留需要的接口范围信息。

客机可以使用发现列表、最近房间或手动输入的主机地址。房间恢复后可以取得新的端口；应用根据相同房间标识更新地址。发现正在等待恢复的房间时触发重连，断线页面也提供手动连接。

`Desktop` 保存一个当前连接。其发送端可以是本机 Host，也可以是远程请求通道。离开房间时释放连接，房主同时结束服务并撤销广播。每个成员的活动连接数量用于判断其是否真正断线。

实现位于 [desktop.rs](../src-tauri/src/desktop.rs) 和 [discovery.rs](../src-tauri/src/discovery.rs)。

## 存档与本机数据

本机数据目录由 Tauri 的 `app_data_dir` 取得，应用标识为 `build.loop.cataland`。macOS 对应 `~/Library/Application Support/build.loop.cataland`；代码统一使用平台返回的目录。

| 内容 | 文件 |
| --- | --- |
| 本机身份、名称、颜色 | `identity.json` |
| 音量、界面缩放、动画、语言 | `preferences.json` |
| 最近加入的房间 | `recent.json` |
| 房主保存的完整房间 | `games/<房间 UUID>.json` |
| 窗口尺寸、位置与窗口状态 | Tauri 窗口状态插件管理 |

房间存档序列化完整 `Room`，包含成员与身份、具体手牌、牌堆顺序、城市状态、回合、效果队列、公开和私有事件以及聊天。随机结果产生后成为状态的一部分，之后的骰子和偷牌继续调用随机数生成器。

写入使用同目录临时文件，再重命名为目标 JSON。首页列出存档时只读取房间摘要与结果，恢复时才解析完整游戏。

进行中的存档重新成为 Host，房主身份取自存档，其他成员先标为离线，之后按各自 token 重新加入。已结束的存档则进入 `Review`，生成本地公共视图。

应用数据与代码仓库分别存放。源代码交接包含规则、资源、生成器和构建配置；特定对局的数据由其房主电脑管理。

## 桌面接口

| Tauri 命令 | 输入 | 作用 |
| --- | --- | --- |
| `session` | 无 | 读取完整 `ClientView` |
| `host` | `settings`、`name`、`color` | 创建并进入本机房间 |
| `join` | `addresses`、`name`、`color` | 连接远程房间 |
| `resume` | `id` | 恢复进行中的房间，或浏览已结束存档 |
| `room_action` | `action` | 发送房间或游戏动作 |
| `leave` | 无 | 离开连接并回到首页 |
| `preferences` | `preferences` | 应用并保存本机偏好 |

`ClientView` 包含偏好、身份、当前房间、连接状态、地址、附近房间、最近房间和存档摘要。连接状态为 `home`、`connecting`、`connected`、`disconnected`、`review`。

## 共享类型与本地化

Rust 侧需要发送到前端的类型派生 `TS`。`pnpm bindings` 从客户端视图、网络请求和响应等入口遍历关联类型，生成 `src/bindings.ts`。类型的序列化名称和前端联合类型由同一份 Rust 定义产生。

规则消息使用 `Text`，形式为原文、带参数的模板或文本列表。中文模板作为词条键，英文译文在 `src/en.json` 中。本机客户端按自己的语言渲染同一条事件，玩家姓名、聊天和外部错误详情作为原文参数。

这让已接收的事件也能随语言切换。列表由客户端的语言格式化功能组合，模板中的数值与名称按占位符替换。

实现位于 [text.rs](../crates/core/src/text.rs)、[locale.ts](../src/locale.ts) 和 [bindings.rs](../crates/core/src/bin/bindings.rs)。

## 棋盘、动画与声音

React 负责页面、面板和动作选择，`BoardCanvas` 创建并持有场景。场景拥有地形层、棋子层和合法位置提示层，使用规则返回的 `Target` 完成命中检测。

棋盘在固定逻辑坐标中绘制，摄像机对整个 DOM 表面应用变换。缩放或归位由浏览器动画插值，完成后根据显示比例调整画布分辨率。输入坐标通过当前可见变换映射回棋盘，因此动画中点击仍对应眼前位置。

棋子状态变化时，场景提取棋子的透明图像，在临时覆盖层中播放移动或出现动画，结束后显示最终的画布棋子。`origin` 与 `target` 提供骑士移动的起终点。资源飞入手牌、骰子、分数变化和野蛮人航程由界面动效处理。

事件序号用于寻找新增事件，初始状态作为显示基线。画布按状态、提示或分辨率变化绘制，导航和棋子插值由浏览器完成。

声音系统在首次交互时启动，以音乐、环境与效果三个通道汇入主音量。音效使用事件种类和新事件序号触发。资源规格与实现细节见[美术与声音](assets.md)。
